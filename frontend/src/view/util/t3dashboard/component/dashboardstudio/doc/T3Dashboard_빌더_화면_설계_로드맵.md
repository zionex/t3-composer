# T3Dashboard 빌더 화면 설계 로드맵

작성일: 2026-06-08

## 1. 배경과 목적

`T3Dashboard`는 `t3-composer` 안에서 대시보드를 만들고 관리하기 위한 컨설턴트용 Dashboard Studio 화면이다. 이 화면은 원래 사용자별 권한과 소유자 기준이 강한 프로젝트에서 가져온 기능을 기반으로 하지만, 이 프로젝트에서는 접근 가능한 컨설턴트가 모든 대시보드를 관리한다는 전제로 방향을 바꾼다.

따라서 이 문서의 목적은 다음 기준을 명확히 남기는 것이다.

- `T3Dashboard`는 허용된 컨설턴트가 사용하는 빌더/관리 화면이다.
- 컨설턴트는 모든 대시보드를 조회, 생성, 수정, 공개범위 조정할 수 있다.
- 일반 사용자는 별도 조회 화면에서 자기 권한에 맞는 대시보드만 볼 수 있다.
- 일반 사용자 화면에서는 대시보드 수정, 삭제, 공개범위 변경, 위젯 생성 기능을 제공하지 않는다.

기존 프로젝트의 "사용자가 자기 권한에 허용된 대시보드만 보고, 자기가 만든 대시보드만 수정한다"는 모델은 이 프로젝트의 `T3Dashboard` 내부 운영 모델로 사용하지 않는다. 대신 빌더 화면과 사용자 조회 화면을 분리해 역할을 단순하게 가져간다.

## 2. 현재 구현 상태

현재 진입점은 `T3Dashboard.jsx`이며, 내부에서 `UserDashboardPage`를 렌더링한다. `UserDashboardPage`는 이름과 달리 현재 기준으로 일반 사용자 전용 화면이라기보다 대시보드 포털 역할을 함께 수행한다.

현재 `UserDashboardPage`가 담당하는 기능은 다음과 같다.

- 대시보드 목록 조회 및 선택
- 선택된 대시보드 조회 및 읽기 전용 렌더링
- 공개범위 필터링 및 그룹 선택
- 공개범위 수정 팝업 호출
- `WidgetBuilderPopup` 호출
- `DashboardBuilderPopup` 호출
- 위젯 선택 후 대시보드 빌더로 전달

현재 권한 관련 단일 진입점은 `auth/currentUser.js`이다. `ENABLE_AUTH=false` 상태에서는 `canEditDashboardAccess()`가 항상 `true`를 반환하므로, 현재 개발 환경에서는 공개범위 수정이 항상 가능하다. 이 동작은 컨설턴트용 빌더 화면이라는 목표와는 맞지만, 일반 사용자 조회 화면까지 같은 컴포넌트를 공유할 경우 수정 기능이 섞일 수 있다.

따라서 앞으로는 "현재 통합 포털"을 그대로 일반 사용자 화면으로 쓰지 않고, 빌더와 뷰어의 책임을 분리해야 한다.

## 3. 목표 권한 모델

`T3Dashboard`의 권한 모델은 컨설턴트용 관리 화면 기준으로 고정한다.

- 이 화면에 들어온 사용자는 이미 컨설턴트 접근 권한을 통과했다고 본다.
- 빌더 화면 안에서는 `created_by`를 기준으로 수정 가능 여부를 제한하지 않는다.
- 대시보드 목록은 컨설턴트가 관리해야 하는 전체 대시보드를 볼 수 있어야 한다.
- 공개범위는 대시보드가 일반 사용자에게 노출되는 범위를 정하는 메타데이터로 취급한다.
- `public`, `group`, `private`은 일반 사용자 조회 화면의 노출 정책에 사용한다.

일반 사용자 화면의 권한 모델은 별도로 둔다.

- 사용자는 자기 권한에 맞는 대시보드만 조회한다.
- 사용자는 대시보드 레이아웃, 위젯 구성, 공개범위를 수정할 수 없다.
- 수정/삭제/공개범위 변경 API는 일반 사용자 화면에서 호출되지 않아야 한다.
- 권한 필터링은 UI에서 숨기는 수준에 그치지 않고 서버 또는 공통 조회 API에서 보장해야 한다.

## 4. 화면 분리 방향

앞으로의 화면 구조는 다음처럼 나눈다.

| 화면 | 대상 | 역할 | 수정 기능 |
| --- | --- | --- | --- |
| `T3Dashboard` | 허용된 컨설턴트 | 대시보드 생성, 수정, 공개범위 관리, 위젯 빌더 실행 | 가능 |
| 일반 사용자 대시보드 화면 | 일반 사용자 | 권한에 맞는 대시보드 조회 및 위젯 확인 | 불가 |

구현 방향은 다음과 같다.

- `T3Dashboard`는 Dashboard Studio 또는 Dashboard Builder 성격의 화면으로 이름과 UI 문구를 정리한다.
- 현재 `UserDashboardPage`에 섞여 있는 조회 렌더링 로직은 재사용 가능한 viewer 컴포넌트로 분리할 수 있다.
- 빌더 전용 액션 영역에는 위젯 생성, 대시보드 생성/수정, 공개범위 편집 기능을 유지한다.
- 일반 사용자 화면은 같은 viewer 렌더러를 사용하되 빌더 팝업과 수정 액션을 포함하지 않는다.
- 일반 사용자 화면의 목록 조회 API는 사용자 권한이 반영된 결과만 반환하도록 확인한다.

## 5. 향후 구현 로드맵

1. 역할 명명 정리
   - `T3Dashboard`를 컨설턴트용 Studio/Builder 화면으로 문서와 UI에서 일관되게 표현한다.
   - `UserDashboardPage`가 계속 빌더 포털 역할을 한다면 이름 변경 또는 래퍼 분리를 검토한다.

2. 공통 조회 렌더러 분리
   - 대시보드 상세 조회, 위젯 정규화, 읽기 전용 그리드 렌더링을 공통 viewer 영역으로 분리한다.
   - 빌더 화면과 일반 사용자 화면이 같은 렌더러를 공유하되 액션 권한은 공유하지 않도록 한다.

3. 빌더 화면 기능 고정
   - 컨설턴트용 화면에서 전체 대시보드 목록을 조회할 수 있도록 API 동작을 확인한다.
   - 선택된 대시보드를 기존 레이아웃 그대로 편집하는 흐름을 보강한다.
   - 공개범위 수정은 빌더 화면 전용 액션으로 유지한다.

4. 일반 사용자 화면 추가
   - 일반 사용자용 메뉴 또는 컴포넌트를 별도로 추가한다.
   - 목록에는 사용자가 볼 수 있는 대시보드만 표시한다.
   - 위젯 최대화 같은 조회 편의 기능은 유지하되 수정 기능은 제거한다.

5. API 경계 확인
   - 빌더 목록 조회는 컨설턴트 권한 기준으로 전체 접근이 가능한지 확인한다.
   - 사용자 조회 화면은 `public`, `group`, `private` 접근 정책이 서버 또는 공통 API에서 보장되는지 확인한다.
   - 수정, 삭제, 공개범위 변경 API가 일반 사용자 화면에서 호출되지 않도록 UI 진입점을 분리한다.

## 6. 주의해야 할 미해결 지점

- 실제 인증이 붙으면 `auth/currentUser.js`의 `ENABLE_AUTH`와 사용자/그룹 조회 방식이 바뀌어야 한다.
- 컨설턴트 접근 권한을 어디서 검증할지 라우팅, 메뉴 권한, 서버 권한 중 책임 경계를 정해야 한다.
- `private` 대시보드가 컨설턴트 화면에서는 전체 관리 대상인지, 일반 사용자 화면에서는 생성자 본인에게만 보이는지 정책을 확정해야 한다.
- 현재 화면의 문구와 일부 주석은 이전 프로젝트 맥락이 남아 있으므로 빌더/뷰어 분리 작업 시 함께 정리하는 것이 좋다.
- 대시보드 수정은 단순 공개범위 수정과 레이아웃/위젯 구성 수정으로 나뉘므로, UI 액션도 명확히 구분해야 한다.

## 7. 정리

`T3Dashboard`는 이 프로젝트에서 일반 사용자 대시보드 화면이 아니라 컨설턴트용 대시보드 제작 및 관리 화면이다. 일반 사용자는 별도 조회 화면에서 권한에 맞는 대시보드만 읽기 전용으로 본다.

이 기준을 유지하면 빌더 화면은 관리 기능에 집중할 수 있고, 사용자 화면은 권한과 조회 경험에 집중할 수 있다.
