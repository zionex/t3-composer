# DB를 모르는 사용자를 위한 Widget Builder 목적 및 구현 가이드

## 1. 작업 목적

본 작업의 목적은 **DB 구조를 모르는 사용자도 단일 위젯을 만들 수 있는 Widget Builder**를 설계하는 것이다.

기존 방식은 사용자가 테이블, 컬럼, 조인, 데이터 구조를 알고 있다는 전제를 가진다.

```text
기존 방식:
테이블 선택 → 컬럼 선택 → 데이터 매핑 → 시각화
```

하지만 DB를 모르는 사용자는 다음을 알기 어렵다.

```text
- 어떤 테이블을 선택해야 하는지
- 어떤 컬럼이 지표인지
- 어떤 컬럼이 분석 기준인지
- 어떤 조건을 걸어야 하는지
- 선택한 데이터로 어떤 위젯이 만들어지는지
```

따라서 Widget Builder의 중심은 데이터 구조가 아니라 **업무 의미와 위젯 목적**이 되어야 한다.

```text
개선 방향:
위젯 목적 선택 → 지표/기준 선택 → 조건 설정 → 데이터 후보 확인 → 시각화
```

---

## 2. 핵심 원칙

### 2.1 사용자는 테이블을 고르지 않는다

DB를 모르는 사용자는 테이블명을 보고 판단할 수 없다.

```text
나쁜 예:
TB_BF_RESULT
TB_BF_LOG
TB_BF_CONTROL_BOARD_VER_MST
```

사용자는 다음과 같은 업무 의미로 판단해야 한다.

```text
좋은 예:
수요예측 결과 데이터
판매 실적 데이터
품목 정보
회의 정보
참석자 정보
```

즉, 사용자가 고르는 것은 테이블이 아니라 **위젯 목적, 지표, 분석 기준, 조건**이어야 한다.

---

### 2.2 컬럼명이 아니라 업무명을 보여준다

물리 컬럼명은 DB를 아는 사용자에게는 유용하지만, 일반 사용자에게는 어렵다.

```text
나쁜 예:
CREATE_DTTM
MEET_ID
ITEM_GRP_CD
QTY
PLAN_QTY
```

기본 화면에는 업무 표시명을 보여준다.

```text
좋은 예:
생성일자
회의
품목 그룹
생산 수량
계획 수량
```

물리 컬럼명은 고급 보기 또는 원본 컬럼 보기에서만 제공한다.

---

### 2.3 위젯은 목적 중심으로 만들어야 한다

사용자는 보통 다음처럼 생각한다.

```text
- 품목별 생산 수량을 보고 싶다
- 월별 회의 건수를 보고 싶다
- 생성자별 등록 현황을 보고 싶다
- 예측 대비 실적을 비교하고 싶다
```

따라서 빌더는 다음 방식으로 흘러가야 한다.

```text
위젯 목적
→ 표시할 지표
→ 나누어 볼 기준
→ 조회 조건
→ 데이터 후보
→ 차트
```

---

### 2.4 AI 없이도 동작해야 한다

현재 목표는 AI 없이도 동작 가능한 업무형 위젯 빌더이다.

추후 AI 또는 Embedding을 붙일 수는 있지만, 기본 구조는 메타데이터 기반으로 안정적으로 동작해야 한다.

```text
현재:
업무 메타 기반 추천

추후:
AI/Embedding이 업무 메타를 검색하고 추천을 보조
```

AI가 SQL을 직접 생성하는 구조보다는, AI가 템플릿/지표/조건 선택을 보조하는 구조가 안정적이다.

```text
좋은 구조:
AI → 업무 템플릿/지표/조건 후보 추천
시스템 → 메타 기반 SQL 생성

나쁜 구조:
AI → SQL 직접 생성
```

## 3. 전체 생성 흐름

단일 위젯 생성 기준 권장 흐름은 다음과 같다.

```text
1. 목적
2. 지표/기준
3. 조건
4. 데이터 후보
5. 시각화
```

각 단계의 역할은 다음과 같다.

| 단계 | 이름 | 역할 |
|---|---|---|
| 1 | 목적 | 어떤 위젯을 만들지 선택 |
| 2 | 지표/기준 | 무엇을 볼지, 무엇별로 볼지 선택 |
| 3 | 조건 | 조회 범위와 필터 설정 |
| 4 | 데이터 후보 | 필요한 데이터 소스 확인 |
| 5 | 시각화 | 차트 형태와 표시 옵션 설정 |

---

## 4. Step 1. 목적

### 4.1 역할

1단계는 사용자가 만들 위젯의 목적을 선택하는 단계이다.

```text
이 위젯으로 무엇을 보고 싶나요?
```

예:

```text
- 생성자별 등록 현황
- 월별 회의 건수
- 품목 그룹별 생산 수량
- 공장별 계획 대비 생산 수량
- 고객별 주문 수량
```

### 4.2 주의점

목적 목록에 기술 키워드나 컬럼명을 그대로 보여주면 안 된다.

```text
나쁜 예:
create_by
agenda_id
meet_id
dttm
```

업무 목적형 표현으로 바꿔야 한다.

```text
좋은 예:
생성자별 등록 현황
안건별 회의 현황
회의별 안건 수
월별 회의 생성 추이
```

### 4.3 우측 영역

1단계 우측 영역에는 단순 숫자보다 다음 정보가 필요하다.

```text
- 선택한 목적 설명
- 만들 수 있는 위젯 예시
- 관련 데이터 후보 요약
- 기존 위젯 존재 여부
- 다음 단계 안내
```

예:

```text
생성자 기준 위젯 만들기

생성자별로 데이터 등록/작업 현황을 확인하는 위젯을 만들 수 있습니다.

추천 위젯
1. 생성자별 등록 건수
2. 생성자별 월별 등록 추이
3. 최근 생성 데이터 목록

관련 데이터
- 관련 테이블 6개
- 기존 위젯 없음

[다음: 지표/기준 선택]
```

---

## 5. Step 2. 지표/기준

### 5.1 역할

2단계는 위젯의 분석 구조를 결정하는 단계이다.

```text
무엇을 볼 것인가?      → Measure
무엇별로 나눠 볼 것인가? → Dimension
```

### 5.2 기본 규칙

```text
- Measure는 최소 1개 이상 필요
- Dimension은 1~3개 권장
- Dimension만 선택된 상태는 지양
- ID성 컬럼은 기본 화면에서 제외 또는 고급 기준으로 이동
- 코드/명칭 컬럼은 하나의 업무 기준으로 묶음
```

### 5.3 데이터가 없는 케이스

숫자형 컬럼이나 명확한 Measure가 없는 경우에는 파생 지표를 자동 추천해야 한다.

```text
추천 Measure
- 전체 건수 = COUNT(ID)
- 생성 건수 = COUNT(CREATE_DTTM)
- 완료 건수
- 삭제 건수
- 메일 발송률
```

### 5.4 데이터가 있는 케이스

Measure와 Dimension이 많은 경우에는 그룹화와 추천 조합이 필요하다.

```text
수량 지표
- 생산 수량
- 계획 수량
- 주문 수량
- 투입 수량

시간 지표
- 공정 작업 시간
- 작업 준비 시간
- 가용 시간

파생 지표
- 계획 대비 생산률
- 평균 작업 시간
```

Dimension도 역할별로 묶는다.

```text
품목 기준
- 품목
- 품목 그룹

고객 기준
- 고객

공장/자원 기준
- 공장
- 인벤토리

상태 기준
- 확정 여부
- 완료 여부

시간 기준
- 작업 시작 일시
- 작업 종료 일시
```

---

## 6. Step 3. 조건

### 6.1 역할

3단계는 사용자가 조회 범위를 좁히는 단계이다.

```text
어떤 조건으로 데이터를 조회할 것인가?
```

조건은 컬럼 선택이 아니라 업무 필터 선택이어야 한다.

### 6.2 나쁜 예

```text
회의체 식별자
참석자 식별자
Agenda 식별자
이슈 식별자
```

### 6.3 좋은 예

```text
기간 조건
- 회의 일자
- 생성일자
- 완료 일시

업무 조건
- 회의
- 안건
- 이슈

사람 조건
- 참석자
- 생성자

상태 조건
- 완료 여부
- 삭제 여부
- 메일 전송 여부
```

### 6.4 기본 추천 조건

가능하다면 다음 조건을 기본 추천한다.

```text
- 최근 3개월
- 삭제된 데이터 제외
```

조건을 선택하지 않은 경우에는 다음 안내가 필요하다.

```text
조건을 선택하지 않으면 전체 데이터를 기준으로 조회합니다.
데이터가 많을 수 있으므로 기간 조건을 설정하는 것을 권장합니다.
```

---

## 7. Step 4. 데이터 후보

### 7.1 역할

4단계는 위젯을 만들기 위해 필요한 데이터 소스를 확인하는 단계이다.

사용자는 테이블을 직접 고르는 것이 아니라, 시스템이 추천한 데이터 후보를 확인한다.

```text
필수 데이터
- 생산계획 결과
- 품목 정보

보조 데이터
- 공장 정보
- 고객 정보

제외 데이터
- 로그
- 임시 테이블
- 백업 테이블
```

### 7.2 관련 테이블이 여러 개일 때 선택 기준

단순 키워드 매칭이 아니라 다음 기준으로 후보를 평가해야 한다.

```text
1. 지표 계산에 필요한 값이 있는가
2. 테이블 역할이 Fact/Result인지 Master/Config/Log인지
3. 선택한 분석 기준으로 그룹핑 가능한가
4. 선택한 조건으로 필터링 가능한가
5. 데이터 Grain이 위젯 목적과 맞는가
6. 필요한 조인 키가 있는가
7. 운영성/최신성 있는 테이블인가
8. 화면 목적과 직접 관련 있는 테이블인가
```

### 7.3 테이블 역할 우선순위

```text
1. Fact / Result
2. Master
3. Calendar
4. Mapping
5. Config / Option
6. Log / History
```

단, 이력 추이 위젯이나 실행 상태 위젯의 경우 History 또는 Log 테이블이 필요할 수 있다.

---

## 8. Step 5. 시각화

### 8.1 역할

5단계는 선택된 지표, 기준, 조건, 데이터 후보를 바탕으로 차트 형태를 정하는 단계이다.

```text
어떻게 보여줄 것인가?
```

### 8.2 추천 기준

```text
시간 기준 + 수치 지표
→ 라인 차트

범주 기준 + 수치 지표
→ 막대 차트

비율/구성비
→ 도넛/파이 차트

상세 목록
→ 테이블

두 개 이상의 비교 지표
→ 콤보 차트 또는 그룹 막대 차트
```

시각화 단계에서는 사용자가 차트를 직접 고를 수 있게 하되, 시스템이 추천 차트를 먼저 보여주는 것이 좋다.

## 9. 필요한 메타데이터

DB를 모르는 사용자를 위한 위젯 빌더를 구현하려면, 각 테이블과 컬럼에 다음 메타데이터가 필요하다.

### 9.1 테이블 메타

```json
{
  "table_id": "TB_FP_RESULT",
  "business_name": "생산계획 결과 데이터",
  "domain": "FP",
  "role": "FACT_RESULT",
  "description": "품목, 공장, 작업 기준의 생산계획 결과 데이터",
  "grain": ["item", "plant", "activity"],
  "metrics": ["production_qty", "plan_qty"],
  "dimensions": ["item", "plant", "customer"],
  "filters": ["date_range", "item", "plant"],
  "join_keys": ["item_cd", "plant_cd"],
  "freshness_type": "current",
  "priority": 1
}
```

### 9.2 컬럼 메타

```json
{
  "column_name": "PLAN_QTY",
  "business_name": "계획 수량",
  "semantic_type": "measure",
  "data_type": "number",
  "unit": "EA",
  "description": "계획된 생산 수량",
  "aggregation": "SUM"
}
```

### 9.3 필수 메타

```text
- business_name
- role
- description
- grain
- metrics
- dimensions
- filters
- join_keys
- semantic_type
- aggregation
```

## 10. 추후 AI/Embedding 확장 방향

현재 구조는 AI 없이도 동작해야 한다.  
다만 추후 AI 또는 Embedding을 붙이려면 지금부터 메타 설명을 풍부하게 쌓아야 한다.

### 10.1 Embedding 대상

테이블/컬럼을 바로 embedding하기보다 다음 순서가 좋다.

```text
1. 위젯 목적
2. 업무 템플릿
3. 지표
4. 분석 기준
5. 조건
6. 실제 테이블/컬럼
```

### 10.2 메타에 포함할 정보

```text
- 업무명
- 설명
- 동의어
- 사용자 질문 예시
- 관련 지표
- 관련 분석 기준
- 관련 조건
- 관련 테이블
```

예:

```text
템플릿명: 품목 그룹별 생산 수량
설명: 품목 그룹 기준으로 생산 수량을 집계해 비교하는 위젯
동의어: 생산량, 생산 실적, 품목군별 생산, 제품군별 생산
질문 예시:
- 품목 그룹별 생산 수량을 보고 싶다
- 제품군별 생산량 비교
- 어떤 품목군이 가장 많이 생산됐나?
```

## 11. 최종 지향점

Widget Builder의 최종 지향점은 다음과 같다.

```text
사용자는 업무 질문을 선택한다.
시스템은 필요한 지표, 기준, 조건, 데이터 후보를 추천한다.
사용자는 의미를 확인하고 최소한의 수정만 한다.
시스템은 메타 기반으로 안전하게 SQL과 차트를 생성한다.
```

즉, 사용자가 DB 구조를 몰라도 다음을 할 수 있어야 한다.

```text
- 어떤 위젯을 만들지 선택
- 어떤 값을 볼지 선택
- 무엇별로 나눌지 선택
- 어떤 조건으로 조회할지 선택
- 추천 데이터 후보 확인
- 차트 저장
```

한 줄로 정리하면 다음과 같다.
